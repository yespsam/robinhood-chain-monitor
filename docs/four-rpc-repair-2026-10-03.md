# Four Registry RPC 修复 · 2026-10-03

## 原因与范围

Four Registry 的日志读取与状态读取都依赖 `rpc-bnb.blockmachine.io`。实测日志中该节点几乎每分钟返回一次 `eth_getLogs` HTTP 429；主机级共同冷却随后使状态验证也失败。Four 的调度器丢失了嵌套错误中的 `retryAfterMs`，每 5 秒重新开始一轮，再撞上尚未结束的冷却。

15:22 左右游标为 125171037，15:32 为 125211997；仍能前进，但远未追平约 125445000 的链头。没有把“进程在线”当成“实时覆盖”。

本轮只修 Four 的读取节点和重试调度，不改购买/卖出逻辑、交易门槛、余额或账本。没有清空、跳跃或重置 Four 游标，没有恢复用户暂停的旧 BSC 待扫任务，没有调用 GMGN / Jev、签名或真实交易，也没有主动发送 TG 测试消息。

## 修改

- 最终默认日志双节点为 NOWNodes + Sentio；状态双节点为 Sentio + NodeReal。仍满足两份独立日志、两份独立状态及至少三个物理主机；Sentio 两种角色共用同一主机预算，绝不算作两个独立主机。保留环境配置覆盖能力；不以一个多节点池冒充一个独立证据来源。
- 一轮默认分段从 4,096 增至 10,000 个区块，不增加并发或轮询频率。已验证的大区间用于追赶，追平后只查到当前确认链头；不跳过范围，不提前提交游标。
- 保留每段两份日志一致、两份状态一致、精确区块哈希、Registry/Core 绑定、运行时代码、规范收据、链重组及持久化边界验证。
- 调度读取嵌套 RPC 错误中最长的必要冷却时间；429 至少退避 60 秒，其他连续故障逐级退避到 60 秒，服务端声明更长时不缩短。成功后回到正常扫描节奏。
- 区分“查询区间太大”与“调用额度耗尽”。429 不再进入区间二分逻辑，避免放大请求。
- 启动日志仅记录选用的主机名，便于核对实际配置；不记录认证路径、参数或密钥。
- 继续使用跨进程共享限流、后台容量和单次恢复探针，不删除锁、不增加并发、不绕过冷却。
