## 后续队列修复（2026-10-09，北京时间 20:30 起）

### 已确认原因

- 20:30–20:32 的只读快照中，1000 个实时保留项有 996 个 Classic Four 创建，均被保守挂到同一批 82 个未解决的报价配置依赖。Classic 创建日志没有报价币字段，不能凭名称、热度或日志缺字段判为无关；旧依赖头的 RPC 重试又阻塞了后面候选。
- 一个 Flap 首三槽位已经持久化收到 `policy_suppressed / terminal=true`，却仍按待投递反复重试。禁止把这种结果伪装成成功发送，也不能以第四个 CA 替补。
- 原单个候选同时请求交易与回执，而共享节点只给后台一个物理槽位。慢请求可使另一个请求耗尽自己的排队／重试预算；新回归用单槽位约束复现了该冲突。

### 本次代码处理

1. Classic Four 通过官方 manager 在**原创建区块**读取 `_tokenInfos`，绑定交易／区块／日志／token，并在读取前后核验 canonical 区块。无历史结果、身份不符、重组、配置变化或保存失败，均不能解除依赖；没有 `latest` 替代历史证据。
2. 每个被证明不匹配的报价依赖才可移除；显式回放、新模板、匹配报价、未知归属保留原检查和因果顺序。未证明不会标为完成，也不产生交易／警报。
3. 饱和队列内允许一个已完成回执归属的实时候选，用原单后台工作槽先补精确报价证明；这个准备步骤只落证据，不完成候选。待独立最终处理重新核验后，才释放保留项。不加并发、容量、等待上限，不挪动历史暂停边界。
4. 精确的不匹配结论与候选热索引一起保存为逐候选回放排除，避免同一个 Classic 创建再触发 82 次无关报价回放。报价配置本身仍保持待验证，不把配置整批标为完成。
5. Flap 仅对明确、持久化、有事件 ID 的终态 `policy_suppressed` 记录独立 suppressed 状态并保留原序号；不记 sent，不刷新前三名，不接受未知／可重试／未落盘的抑制结果。
6. 使用共享节点的精确报价核验，交易与回执改为顺序读取，避免单候选自相争抢后台槽位。普通仅回执分类器的并发和全部共享门控不变。
7. 线上验收发现准备步骤仍可能挤占最终出队名额，已改为：原压力配额到期时先完成已证明独立的候选，再做新准备；独立出队候选中先释放 live 保留项，再处理 base 项。因果未解的任务不能进入此通道，原低频旧任务份额保留；不以清理 base 数量假装释放 live 容量。
