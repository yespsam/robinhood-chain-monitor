# 数据链路可靠性修复（2026-10-01）

## 边界

本轮只改采集、请求调度、诊断和模拟盘；不重置余额、不删除旧扫描任务，不签名或广播真实交易，不续期 Jev，不增加 AI 定时唤醒。现有 TG 过滤和发送规则不变。

## 确认的原因与修复

### 推特覆盖

主关键消息快线的取数预算约 2 秒，公开接口的较慢响应可能被取消；独立叙事源原先只覆盖 Beff/Paid。

- 保留主快线原时限与原身份校验，不延长或伪造其 SLA。
- 独立研究补采扩到 10 个固定数字身份账户：Beff、Paid、CZ、何一、马斯克、币安、币安钱包、Four、Flap、Pon。
- 每轮至多两账户，每账户最多四条原文核验；新增账户不放大并发。轮转位置持久化。
- 保留数值作者 ID、准确作者/状态 URL、发布时间与官方 X oEmbed 核验；回复/引用继续仅作上下文研究，不认定名人背书。
- 请求失败使用持久化递增退避，遵守 Retry-After；服务重载不能重置退避。
- 单条未核验原文以作者 ID + 帖子 ID 单独退避，不能永久占住最新四条的位置。待核验不再显示成完整健康覆盖。
- 此通道只提供研究证据，不直接发 TG 或直接买入。旧原文不回填成首发时点。

上线后已实际补采到 CZ、马斯克、币安、币安钱包、Four 等作者的核验原文。何一、Flap、Pon 完成取数不等于存在当日新帖或可交易 CA。

### RPC 自我拥塞

之前大多数节点只限制日志请求，而收据、区块和代码请求可由多个池并发打向同一物理主机；Flap/Four 的固定校验提供者还使用另一套连接。

- BSC RPC 池按物理主机共享两个请求槽，涵盖日志、收据、区块和状态等方法。
- 等待中的请求取得槽位后再次检查主机冷却，避免前一个请求刚报 429，排队请求又继续打出去。
- Flap/Four 固定校验提供者改用同一 RPC 池机制，每个提供者仍只有一个 URL、没有跨源备用 URL。共享的是容量和冷却，不是校验结果或来源身份。
- 仍遵守已声明的 Retry-After、历史区块标签、独立来源及链 ID 校验。没有把历史状态改查 latest。

### Four 历史交易解析停滞

日志中另有稳定可复现的解析错误：公共节点对交易 `0x6e2b63397fe80c474004f34439fd62e2a749610680b4a4356ce8096399ce5df1` 返回 `type=0x0`、`chainId=""`、`v=0x1c`，ethers 因空链号拒绝解析。

- 仅在原错误明确为 chainId 空字符串时，从同一固定来源读取原交易，不把 429、超时或其他格式错误变成额外请求。
- 由已存在的签名恢复链号，再重建序列化交易并验证交易哈希和发送方；未使用私钥或签名。
- 实测这笔交易是未绑定链号的旧式签名，恢复值为 `0`，不是硬填 `56`。BSC 归属仍由独立节点的实时链 ID、区块、回执和日志一致性证明。
- 对篡改数据、错误发送方、错误哈希、缺失位置及其他链的签名拒绝处理；错误区块仍不得推进游标或发送事件。
- 上线联查又发现池把 ethers 的该类本地 `BAD_DATA` 解码错误计成主机故障，阻挡同源原始读取；现仅对这个确切的旧交易格式错误不打开主机冷却，仍返回错误交给签名复验。429、超时和其他错误保持原限流规则。经过实际单来源池读取的同一交易已复验通过。
- 修复了本地解析阻塞，不代表已经消除 Four 上游限流或完成其历史补扫。

### 钱包证据

通过现有 GMGN CLI 对缓存中的公开地址作只读复查，接口确实返回 `common.created_at = 0`，不是本地把一个有效时间解析丢了。

- 新增明确资格诊断：未采集/过期/身份字段缺失，与已测得但盈利、胜率、样本量等不达标分开记录。
- 保存已有盈利统计，不把缺失年龄填成 0 年、30 天或人为通过。
- 每链输出研究队列人数、已合格/缺证据/不合格数量及原因计数，随资金流诊断供本地策略 API 读取。
- 原资格门槛不变；查询成功不再等同于证据齐全。

### 串行请求间隔

完整并发回归触发了实际的计时问题：共享调度槽写盘后仍有异步文件操作，磁盘繁忙时，原计时点早于真正的请求开始，可能压缩两次串行请求间隔。

- 串行租约释放前持久化本次实际工作开始时间；后续进程据此等待。
- 保持锁与租约、跨进程优先级、正常 Plus 并发策略不变。
- 新增刻意延迟删除排队票据 180 毫秒的测试，验证真实调用间隔仍满足 100 毫秒的测试配置；生产额度没有加大。
