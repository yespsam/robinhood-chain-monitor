## 根因与最小改动

1. 默认 RPC pool 使用 ethers staticNetwork=56，getNetwork 实际只是本地元数据，却曾进入物理请求队列；日志中甚至出现其容量等待失败。缓存成功也可能错误清除共享半开链ID冷却。现在只有构造时确定的默认静态 provider 走本地读取，不申请物理槽、不修改 circuit。自定义工厂仍受原 gate；构造后修改 options 不能绕过。
2. Four 提交后的额外双源核验用于保护事件投递。队列为空时没有投递，现在省下每周期2次 header RPC；提交前双源核验、有队列的提交后复核、下轮实时 anchor 核验均保留。
3. Flap 无待处理事件的区间，在 prepareRange 尾部与 cursor commit 前曾连续核验同一末块。省掉前一次重复终检（每区间4个逻辑调用），保留初检及紧贴提交的双源终检；非空事件与异高度 finalized snapshot 核验不变。

没有增加共享并发（每host总2、background最多1）、队列等待上限、调用预算、频率或确认深度；没有跨周期缓存区块/状态证明，没有替换固定双源。真正的 eth_chainId、区块、状态、日志请求仍经原协调器与冷却。Four本地108次/分钟保守计数也保留。

按 web3-security-trading 的失败关闭边界，链ID错误、双源分歧、重组或校验失败仍阻止相关提交/投递，未知证据不会成为交易许可。
