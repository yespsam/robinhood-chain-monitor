# BSC 历史证据吞吐，第二阶段

范围：接续监控 / 扫链进程隔离，只优化证据获取和有界调度。不改买卖门槛、真实钱包或账本，不清空历史任务。

## 改动

1. 将交易、收据和区块对象读取优先交给现有独立对象 RPC 池；历史合约状态读取仍使用原通道。对象源失败时保留原 archive 回退。两类读取继续受既有跨进程 hostname 配额和冷却约束，未增加共享限额。
2. 进程内最多缓存 256 组已经严格验证的交易 / 收据，120 秒过期。键包含交易哈希、区块哈希、区块高度和交易位置。缓存不持久化、不缓存交易决策；每次复用仍重新读取并验证 canonical block，重新计算当前激活关系和依赖。链重组、错误链或位置错误不能作为成功处理。
3. 深度工作槽中的独立 drain 任务每批最多 4 条、最多 2 个并发处理器。仍仅选原来符合条件的任务，并保留 revision 校验、因果顺序和最终提交。以已记录的独立 Four 创建证据作为低成本排序提示，让可能不需要历史 EVM 状态的任务先使用批量槽；提示不是验证结论，仍完整验证。其他任务保留原 old / dependency / SLA 通道。不是所有待扫任务都可并行，也不是增加无限队列。
4. 将已验证的区块上下文传给后续处理，避免同一任务重复读取区块。普通 Four 的现有快速完成路径仍需要原来的严格收据条件；Flap、模板、升级等证明没有放宽。
5. `_health.receiptProof` 记录对象读取、archive 回退、缓存命中/失效、drain 批次和尝试条数。计数是当前扫描进程生命周期内的，不可当作历史总量；drainEntries 是尝试数，不是完成数。

## 开关与回退

- `BSC_OBJECT_PROOF_ISOLATION_ENABLED=true`
- `BSC_RECEIPT_PROOF_CACHE_ENABLED=true`
- `BSC_INDEPENDENT_DRAIN_BATCH_SIZE=4`（钳制到 1–4）

需要回退时将前两项设为 false、批量设为 1，再平滑重载受监督的 BSC 子进程；不要删除 snapshot / WAL，不要另开第二个扫描写入者。TG/FOMO 无需跟着重启。

## 边界

公共 RPC 的 429 / 超时、历史状态缺失不会由缓存自动修复。若输入长期高于处理速度，40,000 总存储上限仍会产生明确背压。短窗口速度波动不能证明长期清仓速度；未取得真实数据不得把“待扫”改为“完成”。
