# BSC 慢状态读取隔离，第三阶段

## 问题与范围

上一阶段已拆分监控 / BSC 进程、实时容量和对象读取通道。本次针对历史 `getCode` / `getStorage` / `call` 在多个标准、archive 节点间串行重试，造成一个深度工作槽占用数十秒甚至超过一分钟的问题。

只调整 focus3 BSC 扫描器主 RPC 池的状态读取调度，包括同池的 latest 状态读取。交易/收据/日志/区块通道不使用这一状态预算；其已有配额、冷却和验证仍保留。其他监控 RPC 池默认保持原行为。TG/FOMO、策略和账本不在修改范围。

## 实现

- 每次状态读取共享一份预算，跨标准 / archive 回退不重置：默认 10,000 ms、最多尝试 2 个节点。新尝试必须还剩完整的原 transport timeout 和节点租约等待预算。不是在运行中的请求外套更短的 Promise.race：已经开始的请求仍持有原租约，走原有可取消传输。
- 这是启动下一次尝试的预算，不是硬实时 SLA，也不是整个扫描任务的总时长上限；事件循环延迟、有限持久化清理以及一任务里的多个不同状态读取仍可能使任务更长。
- 有界轮换已配置节点，避免每次都只等前两台忙节点。真正的 429 / Retry-After / 方法冷却继续由原跨进程协调器执行；本地预算用完不会添加新的上游冷却，也不会清除已有冷却。
- 相同 RPC 方法、相同完整参数（包含区块标签）在重叠执行期间合并。最多保留 128 个合并键，只存在内存，不输出参数。成功/失败一旦结束就移除，不形成历史或 latest 状态结果缓存；不同区块、不同方法绝不混用。
- 标准/archive 名额使用 FIFO 转交，预算过期的等待者移出队列，不会稍后幽灵占用名额；本地物理节点等待也支持退出。网络请求不会因“外层放弃等结果”而被提前释放租约。
- `rpcBudgetExhausted` 属于单任务、方法级可重试失败。原记录保留在 deferred 证据队列，不能标为 seen / completed。此类本地退让不再额外探测区块高度或触发全链门控。真实上游故障仍按原逻辑处理。
- 健康数据位于 `_health.receiptProof.stateReads`：calls / joined / succeeded / failed / exhausted / endpointAttempts / active / lastDurationMs / maxDurationMs，以及池内 active / waiting。均为当前子进程计数；端点尝试包含本地配额拒绝，不等于实际发出的网络请求数。

## 开关 / 回退

- `BSC_STATE_READ_BUDGET_MS=10000`；设 0 恢复原状态读取回退，关闭这层合并。
- `BSC_STATE_READ_MAX_ATTEMPTS=2`；范围钳制到 1–4。
- 保持默认 7 秒 transport timeout 时，10 秒预算允许一次慢尝试，或最多两次较快尝试；节点租约等待预算计入启动预留。
- 只需平滑重载受监督的 BSC 子进程。不要改账本、删 WAL / deferred 记录，或并行启动第二个状态写入者。

## 保留限制

有界退让不能凭空补出不可用的历史合约状态。方法不可用的任务仍需要可用来源才能完成；deferred 不等于完成，不可只看 pending 下降来宣称消除积压。不同历史区块不会错误复用代码，因而部分批次的合并命中可以很低。调度优化不等于新增交易或策略盈利。
