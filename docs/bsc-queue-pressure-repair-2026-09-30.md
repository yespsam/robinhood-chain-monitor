# BSC 队列拥塞修复（2026-09-30）

## 根因和修改

1. 收据分类只缩小因果依赖，不算完成；其完成路径反复重置普通工作配额，连续分类可饿死最终处理。增加独立分类批次计数，连续两批后给已到期、无活动 SLA 抢占的最终处理一个时隙。
2. 历史和实时共用容量。新增仅限近头 HTTP / WebSocket 的 1,000 条实时预留；旧事件不能伪装实时占用。原历史硬上限仍为 25,000，待处理硬上限为 26,000，连同 deferred 的总上限为 40,000。
3. 提前背压：待处理达到 20,000 或总待处理达到 30,000 时暂停新增历史入队；分别回落至 15,000 / 25,000 后恢复，避免阈值附近频繁切换。高水位时仍处理已有证据、允许新实时事件；历史区块游标保留。
4. 新鲜候选的旧依赖可以获得有限调度份额，不再被大量无关旧记录挡住；同一个因果组仍严格按链上顺序处理。
5. `_health.queuePressure` 记录实时/历史入队、真正完成数量、剩余实时容量和最后完成时间。高水位连续五分钟未完成候选记为 stalled，写入限频本地告警；收据分类和转移到 deferred 均不能冒充完成。
6. 每分钟记录到达/完成速率，即使仍有少量完成，只要处理速度低于到达速度，也明确标记 overloaded，不冒充恢复稳定。
7. Four.Meme 模板/底池先验证事件时间窗和请求键，再请求 token API / `_tokenInfos`。不可能与当前激活事件匹配的旧币不再反复查询新模板。
8. focus3 本来就不播报的普通管理器创建事件，在规范收据已校验、没有活动模式/因果依赖、不是重放任务、没有 Hook/升级/生命周期任务时完成发现归类。仍保留原有 seen 与创建事件热索引，不再重复构建不会改变监控决策的完整合约画像；它不代表安全合格，也不会成为交易候选。活动模板和显式重放仍走完整路径，后到的官方激活可以通过已有热索引重放流程重新研究。GMGN / 叙事模拟候选的交易校验没有改变。

所有批次仍是候选与游标一次落盘。容量拒绝不删除已有记录、不标记 seen、不跳过区块、不推送交易、不绕过安全检查。

## 验收口径

## 第二轮：RPC 冷却作用域（2026-10-01）

00:13 上海时间的实际证据：深度队列因 `getCode` 进入 240,760 ms 全局暂停，但错误内的归档池最早重试仅需 474 ms；独立实时日志仍健康。待处理 25,948、deferred 5,278，累计仅完成 57 条。原逻辑将「任一主机的最长 429 证据」当成「全部深度工作都不可用」，是新的队头阻塞。

- `rpcHostRetryAfterMs` 只保留为单个主机的诊断证据；只有聚合错误明确为全部物理主机不可用才暂停整个深度队列。
- 标准/归档是可替代数据源，合并错误采用最早可用重试时间，而非最长时间；每台物理主机的独立冷却和半开探测锁仍强制执行。
- 一台半开探测失败不会把另一台可探测节点一并封锁。
- 仅 `getCode` 不可用时，候选完整保留在 durable deferred，不能标记安全通过或成交；不相关任务可以继续，相关因果组仍按原顺序等待。
- 整个日志方法池不可用仍暂停对应日志恢复通道，禁止失败后展开海量逐块收据请求；不会误扩散到其他方法的研究通道。

回归覆盖混合 429/方法超时、全主机 429、5 秒/240 秒异步恢复、跨重启保留全局冷却、独立候选可继续、日志冷却不扩大请求，以及半开节点之间的独立恢复。部署和吞吐结论以之后的线上实测为准，不把单测通过等同于已消除积压。

### CPU 热点实测

最后一轮短时本地 CPU 采样持续 5,925 ms，其中 `outstandingFlapActivationReplay -> buildBscOutstandingCausalHeads` 约 1,804 ms。重放仅判断是否存在任务，却为每个激活反复合并全部队列、构造所有因果组的队头。改为无排序、可提前返回的存在性检查；排队顺序、组锁、提交阶段仍使用原完整头部算法。存在任务时也不再提前构造重放候选列表。深度工作器已占用时，唤醒函数直接返回，由原 owner 的 finally 安排下一次，避免无用地重算 3 万条 eligibility。
